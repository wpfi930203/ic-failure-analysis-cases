## Accurate Memory Bitmapping based on Built-in Self-Test:   Challenges and Solutions  

Lin Zhao 1 , YT Ngow 1 , SH Goh 1 , YH Chan 1 , Hao  $\mathrm{{H}}\mathbf{{u}}^{1}$  , F Jeff 2 , CC Tay 2   1 GLOBALFOUNDRIES, Product Diagnostic Engineering, Singapore  2 Mentor - A Siemens Business

## ABSTRACT  

Bitmapping commonly refers to the localization of memory  defects prior to physical inspection. With the pervasive use of  embedded memories in modern silicon-on-chips (SoC),  memory built-in self-tests (MBIST) become the only means to  access and evaluate the memory cells. In the event of a failure,  the accuracy of defect isolation depends heavily on the quality  of MBIST diagnostic to acquire the correct failing details.  Although the workflow to enable diagnostic is well  established, challenges exist during actual implementations  leading to errors in localization. Based upon the authors’  experiences, this paper seeks to highlight possible areas of  concern and describe solutions to overcome them.

## INTROUCTION 

In general, localization of memory defects can be classified  into software and hardware-based methods. The latter refers to  electrical failure analysis techniques, mostly photon emissionbased techniques applied both statically [1] and dynamically  [2, 3]. Laser stimulation approaches have also been  demonstrated [4]. Although they are effective, software-based  bitmapping approaches are still preferred as mainstream  because of its faster turnaround time and better throughput.  Since contemporary SoCs constitute a significant amount of  embedded memories, at-speed BIST in contrast to direct  memory accessing, is the most efficient test methodology due  to test time and limited pinouts constraints. The tradeoff  however, is an additional post-diagnostic step to obtain the  electrical fail address to guide defect physical inspection.

## Concepts of Memory Diagnostics 

Figure 1 shows a typical MBIST architecture. An IEEE  standard 1149.1 test access pins (TAP) controller or  commonly known as JTAG is usually implemented in  conjunction to enable data transfer between external pins and  the BIST controller. It consists of four mandatory signals  namely test clock (TCK), test data input (TDI), test data  output (TDO), test mode select (TMS) and test reset (TRST).  The MBIST controller and embedded memory block are the  two main components in the design. The former consists of a  Finite State Machine (FSM) controller, address generator, data  generator, control builder and comparator. At the start of the  MBIST test, the FSM generates a sequence of patterns to  evaluate the memory cells. The address generator and data

generator provides the address sequence and data to be written  into the cells. The control builder coordinates the read/write  operations. Upon test completion, an MBIST “DONE” signal  will be generated by the MBIST controller. In the next step,  data readout from the memory blocks is compared against  expected data within the comparator logic to determine the test  state as indicated by a Pass/Fail flag (MBIST “GO” Signal)  for each MBIST block. The MBIST test terminates.

For diagnostic, a bitmapping procedure is required. This  generally involves scanning out the latched values from data  registers into a log file via the BIST controllers. The log  contains information about the electrical address of defective  memory cells. A further diagnosis step is required to translate  them into their corresponding physical locations in the chip to  guide physical inspection.

Figure 2 shows a typical bitmapping flow based on mentor  graphics MBIST IP [5]. The entire process to acquire the  physical coordinates can be divided into four main efforts:

1) The creation of a characterization and debug package    (CDP),     2) Test development,     3) Diagnosis and     4) Electrical to physical address scrambling.

## Overview 

In practice, challenges exist in the deployment of bitmapping  for embedded memories defect localization. A complete  validation to confirm the accuracy of a bitmap setup using  laser stimulation approaches - either SDL or high resolution  laser marking [6, 7, 8] is necessary to qualify the setup. When  bitmapping is discovered to be inaccurate and the root cause is  not a result of human errors, oftentimes, the affected memory  blocks are identified and not considered for analysis due to the  complexity of debug. In the worst case, the setup is abandoned  and hardware-based approaches are relied upon. Currently,  there is little discussion in literature to provide guidance in  debugging an inaccurate bitmapping outcome. This paper  seeks to fill that knowledge gap. The rest of the paper is  organized as such: The next section introduces the two main  types of MBIST diagnostic methods based on Tessent IP.

Possible areas of concern will be discussed before we present  a   comprehensive   workflow   in   enabling   an   accurate  bitmapping. Some case studies will then be presented before  we conclude.

## TYPES OF TESSENT MBIST DIAGNOSTIC 

There are two types of design database that support the setup  for bitmapping, namely Logic Vision (LVDB) and Tessent  Shell (TSDB). Both online and offline diagnosis are possible  on LVDB and TSDB.

## Stop-on-Nth Error (SOE) 

Online diagnosis is also commonly referred to as the SOE  workflow as shown in figure 5. The LVDB and design  memory configuration files are required to generate a CDP  package which consists of critical files like test patterns and  data register map. The test patterns are required to develop the  diagnostic test program. During testing, whenever a data readback mismatch occurs, the BIST controller latches the failure  address and executes a scan-out to the log file before resuming  test. This process terminates after the Nth error is obtained.  The main differentiation and key advantage of online  diagnosis lies in the interpretation of electrical to physical  address. For SOE, this is accomplished within the test program  via translational scripts which have to be coded. The next subsections describe two possible problem areas that could result  in an inaccurate diagnosis.

The electrical addresses are then translated into  physical coordinates. In contrast, this step is accomplished  within the ATE for SOE online diagnosis. Although more  steps are involved, the faster throughput of a few times is  attractive. ## A. Relationship between Test Time Multiplier (TTM)  and TCK   

The BIST controller has a design reference clock frequency  which is defined in the designName.summary file. According  to the MBIST architecture as shown in figure 1, data external  to the BIST controller communicates via the TAP. The data  frequency is determined by the TCK clock frequency. This  information is found in the manufacturing configuration file  (designName.etManufacuring). Figure 9 illustrates extracts of  both files with the interested attributes in highlight. The test  time multiplier (TTM) extends the MBIST run time by adding  repeated cycles into the test patterns. This is necessary to  ensure that the test time is long enough for the instruction  from the TAP to properly initialize the state machine in the  BIST controller. The minimum TTM is defined as:

$$\begin{array}{r}{T T M m i n=\frac{B I S T\,C L K\,(M H z)}{T C K\,C L K\,(M H z)}}\end{array}$$
(1)

When TTM is less than the minimum TTM required for all  controllers, the patterns do not pass on a good die. Some  random fail cycles that are not relevant to bitmapping are  generated. These cycles exist in real memory fail dies as well  together with the actual fail cycles. When TTM fulfils the  requirement, only actual defect fail cycles will be shifted out  and the diagnostic result is more accurate than the result with  insufficient TTM.

By tradition, online and offline diagnosis is usually associated  with SOE and ESOE respectively. Figure 10 presents a  proposed cheat sheet in the form of a checklist that highlights  the critical aspects in each workflow. The entire process is  classified into three phases namely, 1) test patterns and CDP  preparation, 2) test and fail logging and 3) diagnosis. In the  first phase, there are no significant differences between SOE  and ESOE. It is important to refer to “pattern name” from the  manufacturing configuration file (TSDB/ LVDB) and assign  its corresponding name as part of the naming convention for  all the patterns to be created as well as the key word in the fail

logs. In the same manufacturing configuration file, it should  also be checked that the “CompareGo” and “CompareGoID”  pins are enabled for intended controllers to be tested and  diagnosed. To calculate TTM according to equation (1),  “ClockPeriod” together with “BistClkFrequency” as specified  in the summary file (.summary) can be used.  Prior to the  generation of test patterns and the CDP package, it is also  important to ensure that the TAP design pins (TDO, TCK,  TMS, TDI & TRST) are mapped to tester channel names  correctly.

For the second phase, some efforts are expected to ensure the  correct initialization for all pins, both JTAG pins and IO pins,  to configure the device into the correct functional mode during  diagnostic testing. Prior to the diagnosis phase, it is a good  practice to validate the fail cycles of any fail dies and  determine any cycle offsets to be accounted for in the test  program by comparing the fail cycles with the contents found  in the register map file. “GO” and “DONE” are two obvious  cycles for validation. Consider the case of large discrepancies;  it is likely that phase 1 has gone wrong.

In fact, the main difference between SOE and ESOE lies in the  final phase of diagnosis. To accomplish online diagnosis for  SOE flow, “Mem_inst_coord.dict” and “bit_coord.dict” files  are created and incorporated into the test program for mapping  from electrical to physical chip-level coordinates. Both  “Mem_coord.dict” and “bit_coord.dict” contains look-up  information such as the memory instance coordinate, offset  and orientation of SRAM blocks as well as the bit cell  electrical to physical translation. For ESOE, phase 3 can be  divided into two parts. The first part translates fail cycles  (JSON format) into electrical address. The second part  comprises the the electrical to physical scrambling translation  It is important to ensure that 1) the JSON fail log and  diagnosed report shares the same bitmap header and 2)  “UserTestName” in the JSON fail log shares the same as  “PatternName”   as   specified   in   the   manufacturing  configuration file.

## CASE STUDY  

## Bitmap Error 

This case involves a SoC product. The bitmap has been  enabled but physical inspection reveals no visual anomaly.  Programmed defects using continuous wave 1340 nm  wavelength laser on point mode are created on two good dies  to confirm the bitmap error as shown in Figure 10. Figure 11  illustrates the impact of a wrong data register sequence. A  laser programmed defect is created on a different good part  and evaluated on bitmap. It is found that XZY is the order of  addressing in order to match to the defect location.  Following  the order in the register map of ZXY, the discrepancy is more  than 150 microns away.

The finding ascertains that a programmed defect step [7-10] is  necessary to deduce the correct registers sequence for accurate  bitmap addressing.

## TTM setting experiment 

In this case study, different TTM settings are specified in the  manufacturing configuration file to study its effect to the  diagnostic outcome. TTM=35 (less than TTMmin) and  TTM=40 (equal to TTMmin) are applied.

## A.   Effect of TTM on pattern length  

The function of TTM is to control the memory BIST run time.  This is clear by the addition of repeated loop cycles in the  diagnostic patterns as discussed earlier in section 2. There are  two ways to configure TTM in the manufacturing file. A  different TTM setting can be applied to each individual BIST  or a single TTM value can be applied to all controllers.

Nevertheless, the number of repeated loops in the diagnostic  patterns will follow the maximum number of TTM setting.  Table 3 shows the evidence.

## B.   Effect of TTM on fail cycles and bitmap result   

Table 4 compares the fail cycles obtained using TTM35 and  TTM40 test patterns. It should be mentioned that the cycle  offsets have been removed so that a direct comparison can be  achieved. It is obvious that TTM35 patterns generate more fail  cycles than TTM40 patterns. However, the failing electrical  addresses in the bitmap report are similar. The additional fail  cycles generated by TTM35 are redundant. These cycles are  DONE flag and error step counter without GO_ID information  which contain the failed register details, hence, are ignored  during post-diagnosis translation.

Based on actual MBIST fail dies with multiple fail bits and  single bit fail, the bitmap results for TTM35 and TTM40 are  compared and presented in figure 12(a) and 12(b) respectively.   TTM40 is the minimum number to satisfy all BIST  controllers. Figure 12(a) shows an additional defect  (encircled) in the case of TTM40 for multiple fail bits  whereas, no significant difference is observed for the case of  single bit fail. It is noteworthy that these are just two case  examples and do not represent all situations of TTM lower  than the minimum threshold. Although the difference is small  when the TTM is close to threshold in this example, some  stability and inaccuracies are evident. It should also be  mentioned that for TTM lower than threshold, the good dies  are failing which is not desirable. Therefore, it is highly  recommended to assign TTM to be at least its minimum  required for accurate isolation.

## CONCLUSION  

Memory failures are typically one of the highest yield loss  contributors to a product. It is important to uncover any  memory failure root cause fast in order to ensure timely  product time-to-market. Therefore, defect localization which  is a critical step in failure analysis is pivotal. It narrows the  physical search area drastically. In this paper, we have shown  that bitmap errors exist. Bitmapping cannot be assumed to be  accurate and deployed for fault isolation without validation.  Oftentimes, there is no fixed workflow to debug an error in  bitmapping and the ownership of solving the problem is  unclear because it involves a multi-domain knowledge team to  work together. In their individual domain, it is not obvious  where to start the debug. With the motivation to fill the gap,  we present possible problem areas in an MBIST setup that can  lead to an inaccurate localization. A cheat sheet in the form of  a checklist is proposed for a comprehensive debug to achieve  an accurate bitmap outcome.
